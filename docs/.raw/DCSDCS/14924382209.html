Introduction

The Patient Data Manager FHIR API enables NHS products to store, retrieve, and manage Patient health and care data in a standardised, interoperable format.

See Patient Data Manager FHIR API for further information.

Requirements

Applicable Suppliers

ID

Requirement

Level

GP Suppliers

PDM01

Implement and maintain the Patient Data Manager FHIR API requirements inline with the latest specification version as per the Patient Data Manager FHIR API Operations section.

MUST

PDM02

The Patient Data Manager FHIR API is called to get a specific FHIR resource when a notification event from the Multicast Notification Service (MNS) is processed.

MUST

PDM03

The Multicast Notification Service (MNS) notification event will be processed in an idempotent way.

MUST

PDM04

After receipt, regardless of ingestion outcome of the FHIR resource, the Solution shall create a resource acknowledgement in the Patient Data Manager FHIR API according to the FHIR Acknowledgement framework.

The acknowledgement will cover both success and failure scenarios.

MUST

PDM05

Performance - Get a specific FHIR resource

The Patient Data Manager FHIR API is called to retrieve a FHIR resource within 30 seconds of receiving the MNS event notification, measured end-to-end.

MUST

PDM06

Performance - Data Ingestion

The ingested FHIR resource will be processed and made available in the GP IT Solution within 2 minutes of receipt of the FHIR resource from the Patient Data Manager FHIR API, measured end-to-end.

MUST

PDM07

Performance - Acknowledgements

A resource acknowledgement shall be sent to the Patient Data Manager FHIR API within 5 minutes of FHIR resource ingestion.

MUST

PDM08

Reliability - Retry

The system will attempt a minimum of 3 retries (with an option to extend to 5) before classifying a request as failed.

Each write operation should include an idempotency key. When retrying the same operation, use the same key to prevent duplicate processing.

As in line with PDM-009.

Examples may include, but are not limited to:

  • Create a resource

  • Get a specific resource

MUST

PDM09

Reliability - Exponential Backoff Strategy

Retry logic for failed request processing will follow an exponential backoff strategy to prevent system overload and ensure safe reprocessing.

Examples may include, but are not limited to:

  • Create a resource

  • Get a specific resource

MUST

PDM10

Reliability - Dead Letter Queue (DLQ)

Un-processable events or requests stemming from background processing to be published to a DLQ for investigation and out-of-band processing.

Examples may include, but are not limited to:

  • Create a resource

  • Get a specific resource

MUST

PDM11

Reliability - DLQ Retry

The cause of failure and events or requests in the dead letter queue (DLQ) to be retried after the cause of failure has been resolved, within 1 working days.

Examples may include, but are not limited to:

  • Create a resource

  • Get a specific resource
